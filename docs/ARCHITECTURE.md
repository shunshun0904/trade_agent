# アーキテクチャ

仕様書 §3 の論理構造と、それを実装に落とすときに下した判断の記録。
「なぜそうなっているか」がここに書いてある。

## 全体

```
EventBridge Scheduler
   ├─ 5分  → tick    ── SL/TP評価・キルスイッチ・pending突合・ハートビート  (LLM不使用)
   ├─ 30分 → screen  ── 決定論トリガー評価 → 成立時に decide を非同期invoke  (LLM不使用)
   └─ 9:00/21:00 JST → screen(定時フロア)

decide ── オーケストレータ + A1〜A4 + 決定論ガード + 発注
reflect ── 決済完了トリガー、A7、Batch API 可
mcp ── Function URL、オーナー対話(プル型)

DynamoDB × 9  ── state / orders / locks / trades / agent-calls /
                 lessons / equity-curve / daily-reports / audit
S3 × 1        ── エージェント入出力本体・ペーパー口座・日次バックアップ
```

## 判断の記録

### 数値は Python が確定させる

LLM は価格も損益も計算しない。`MarketSnapshot` が「確定値 JSON」であり、
モデルが引用した指標値は決定論ガードが実値と照合する
(`guards/deterministic.py` の `check_quoted_indicators`)。

照合は「現在値としての言明」だけを対象にする。`RSIは58.1` は照合するが、
`RSIが70を超えたら` は閾値の話なので照合しない。この区別がないと、
正常な戦略記述が誤検知で棄却され続ける。

### 合意ルールは Python が数える

2案中1案以上が buy でなければ no_trade。裁定者(A3)には
「buy が何件で、必要な件数がいくつか」を伝えるが、判定そのものは
`cycle.py` の `_adjudicate` が行い、ガードが裁定者の出力と照合する。
裁定者が自分で条件を緩められるなら、それはルールではない。

### エージェントは7体 —— 検査官と指揮官は置かない

仕様 §4 は9体を定義しているが、実装は A5(検査官)と A6(指揮官)を持たない。

**検査官** は「LLM が LLM を検査する」層だった。数値検証は決定論ガードが
すべて行っており、検査官に残るのは定性的な矛盾探しだけで、それは4つの
検査の中で最も当てにならない種類のものである。

**指揮官** の GO/NO-GO は、合意ルール(Python)・サイジング(Python)・
リスク査定(A4)・`check_executable`(Python)をすべて通過した後に乗る
5つ目の拒否権だった。Python が既に確定させた判断を、モデルが言葉で
覆せる経路を2つ減らしたことになる。

残る関門は5つ、うち4つが決定論的:

| 関門 | 実装 |
|---|---|
| 合意ルール(2案中1案) | Python |
| 各エージェント出力の検証 | Python(決定論ガード) |
| ポジションサイズ算出 | Python |
| リスク査定 | **A4(LLM)** |
| 最終構造検査 `check_executable` | Python |

### オーナー向けレポートは Python が組み立てる

指揮官が唯一やっていた冗長でない仕事である。ただしレポートを書く時点で
材料はすべて構造化済みのフィールドとして存在している —— レジーム判定、
提案数、裁定理由、リスク査定、価格と数量。これをモデルに言い直させても
得るものはなく、**実際に起きたことと食い違う経路が増えるだけ**である。

そこで `orchestrator/report.py` が数値と体裁を担当し、エージェントの文章は
そのまま引用する。レポートの各行は `agent_calls` か `trades` のフィールドに
辿れる。仕様 §14 が求める「外部から判断過程を監査できる」とはこのことである。

### 安全装置は LLM の前に評価する

キルスイッチ・日次損失・連敗・急変動・予算のすべてがスナップショット取得直後、
最初のエージェント呼び出しより前に評価される。停止中のシステムは1トークンも
使わない。`test_the_kill_switch_stops_the_cycle_before_any_llm_call` が
`llm.calls == []` を assert している。

### 二重発注に対する3重の防御

| 層 | 仕組み | 防ぐもの |
|---|---|---|
| decide ロック | DynamoDB 条件付き書き込み + リース TTL | 同時刻の多重起動 |
| サイクルロック | `cycle:<id>` を取得して解放しない | 同一サイクルIDの再実行 |
| 注文ID | `sha256(cycle_id + ":entry")` で決定論的に生成 | 上2つを抜けた再実行 |

3つ目が効くのは、順序が「DB に `pending` を書く → 取引所を呼ぶ」だから。
逆順だと、書き込み前にクラッシュした注文が痕跡なしに消える。

### 突合できないときは止まる

bitbank にクライアント注文IDがないため(docs/OPEN-QUESTIONS.md A-2)、
`pending` 行と取引所注文の突合は形状マッチになる。候補が複数ある場合、
どちらが自分の注文か判定できない。このとき **再発注は絶対にしない**。
`UNKNOWN` を記録してオーナーに通知し、人間の判断を待つ。
仕様 §6「判断できないときは何もしない」の適用。

### 独立提案の証明可能性

仕様 §4.1 は各案が相互不可視であることを求め、§14 は
「ログで検証可能」であることを求めている。実装では
`agent_calls.saw_agents` に、そのコールのプロンプトに出力が含まれていた
エージェント名を記録する。フェーズ1の戦略エージェントは `["analyst"]` のみ。
MCP の `get_agent_log` が `independent_proposals_verified` を返し、
外部から検証できる。

### プロンプトキャッシュ

構造は仕様どおり。

```
system[0]  共通プレフィックス  ← cache_control: ephemeral(サイクル内で全エージェント同一)
system[1]  役割指示           ← エージェントごとに異なる
messages   タスク入力
```

キャッシュは前方一致なので、共通部分が先頭かつ **バイト単位で同一** である
必要がある。`AgentRunner.set_prefix()` がサイクル開始時に1度だけ組み立て、
以後は同じ文字列を使い回す。`test_the_shared_prefix_is_identical_across_agents`
がこれを固定している。

ただし最小キャッシュ長はモデルごとに違う(`claude-sonnet-5` は 1,024、
`claude-haiku-4-5` は 4,096)。共通プレフィックスは約3,800トークンなので、
現状のプレフィックス(約2,000トークン)はこれを下回るため
**実際にはキャッシュが作られない**。エラーにならず静かに全額課金されるので、
`AgentRunner._warn_if_uncacheable()` が WARNING を出し、
`agent_calls.cache_read_tokens` に実績が残る。
判断の選択肢は docs/OPEN-QUESTIONS.md A-4。

### Decimal のみ

価格・数量・JPY はすべて `decimal.Decimal`。float は指標計算の内部にも
持ち込んでいない(RSI も ATR も Decimal 演算)。理由は2つ。ガードが
「モデルの引用値と実値の一致」を判定するため、丸め誤差が捏造判定に化けると困る。
そして DynamoDB は Decimal をそのまま保存でき、float を経由する必要がない。

エージェントの JSON 出力だけは float で受ける(JSON に Decimal がないため)。
ガードの境界で Decimal に変換し、以後は Decimal で扱う。

### DynamoDB を常時無料枠に収める

Always-Free は **プロビジョンド** 25 RCU / 25 WCU で表現されている。
オンデマンドの無料枠は12ヶ月限定なので、全テーブルを 1 RCU / 1 WCU の
プロビジョンドにしてある(合計 9 RCU / 10 WCU)。

GSI を1つも作っていないのも同じ理由(1つごとに容量が要る)。
キー検索にならない2つの一覧(`orders.list_open`、`trades.list_*`)は
Scan + Python 側フィルタ。アイテム数が数百のうちは1 RCU の端数で済む。

### ペーパー取引所は悲観的に約定させる

Phase 1 の合格基準は「手数料込み期待値がプラス」(仕様 §13)。
楽観的なシミュレータはこの基準を自分で作り出してしまう。

- 指値買いは、板が指値を **下抜けたとき** だけ約定(タッチでは約定しない)
- 損切りはテイカー手数料、利確はメイカー手数料
- 同一足で SL と TP の両方に触れた場合は **損切り優先**

同じ規則をバックテストエンジンにも適用してある。

### bitbank のメイカーはリベート

メイカー手数料は **-0.02%(受け取り)**。したがってメイカー往復のトレードは
手数料が黒字になる。バックテストは事実としてこれを反映するが、
決定論ガードは往復コストを上回らない利確幅を棄却する。リベートに依存した
利確幅は、リベートが変われば消えるからで、それは戦略ではなく料金表である。

### 自作OCO — 損切りは取引所側、利確はローカル

bitbank に OCO エンドポイントは無いので、2脚を個別に発注し、片方の約定を
検知して他方を取り消す(`execution/protection.py`)。

現物での結論は **損切りだけが取引所側に載る** である。理由は残高:
利確の指値売りがBTCを拘束すると、損切りが同じBTCを確保できない。
そして拘束のタイミングが「トリガー時」の取引所では、両脚を出すと
**利確が損切りの残高を奪い、発動時に損切りが拒否される** —
注文一覧上は保護されて見えるのに実際は無保護、という最悪の状態になる。

そこで `arm()` は、両脚が受理されても残高照会で裏付けを検証し、
両方を裏付けていなければ **利確脚を取り消して損切りに残高を返す**。
どちらの挙動の取引所でも、損切りが残高を握る側になる。

脚の順序も同じ理由で決まっている。**損切りを先に出す。**
1つしか置けないなら、置くべきは保護する側である。

ローカル評価は消えたわけではなく、**バックストップとして常時armされている**。
`_exchange_holds()` が「その水準を取引所側の生きた脚が持っているか」を
注文ステータスで確認し、持っていない水準だけをローカルが見る。
だから二重売却は起きず、損切り脚が REJECTED になった瞬間に
ローカルが引き継ぐ。

ローカル決済を出すときは、先に取引所側の脚を取り消す。拘束された残高は
売れないからで、記録が古くて取り消せなかった場合に備えて、残高不足で
弾かれたら取引所へ直接キャンセルを投げて1回だけ再試行する。

### tick が死んでも損切りは死ななくなった

取引所側に損切り注文が載っている限り、このプロセスが止まっても損切りは働く。
当初の設計(SL/TPともローカル評価)にあった構造的欠陥はこれで解消した。

ただし `tick` のハートビートアラームは安全要件のままである。利確はローカル、
建玉の追跡もローカルであり、損切り脚が拒否・消失したときに気づけるのも tick
だけだからである。
