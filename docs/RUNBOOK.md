# 運用手順

## まず: 本当に動いているか

```bash
cd ~/trade_agent && bash scripts/status.sh
```

読み取り専用。スタックの状態、各関数の起動回数とエラー数、ハートビート
アラーム、DynamoDB に実際の作業痕跡があるかを見て、最後に判定を出す。

**「スタックがデプロイできた」と「システムが動いている」は別の主張である。**
毎回例外で落ちるスケジュール実行の Lambda は、CloudFormation 上は完璧に
健全に見える — スタックは CREATE_COMPLETE、スケジュールも存在し、赤くなるのは
誰も見ていないメトリクスだけ。このスクリプトは後者を証拠から判定する。

判定が `NOT RUNNING` なら、tick のログを続けて表示するので原因が分かる。

## 緊急メールが来た

### 「キルスイッチ発動」

初期資金から -20%(equity 8,000円割れ)。全建玉のクローズを試行し、
新規建てを完全停止した状態。

1. Claude のチャットから `get_status` で建玉が本当に閉じたか確認
2. `get_trades` で直近の損失がどのトレードで出たか確認
3. `get_agent_log` でそのトレードの判断過程を読む
4. 原因が腑に落ちるまで再開しない

再開:

```
resume_trading を confirm=true で実行してください
```

**キルスイッチは時間では解除されない。** 明示的に再開するまで止まったまま。
連敗ブレーキと急変動停止は `resume_trading` では解除されない(時間経過で切れる)。

### 「tick-heartbeat」アラーム

**最優先。** 5分tickが15分以上動いていない。取引所側 OCO がないため、
**建玉があれば損切り監視が止まっている。**

1. CloudWatch Logs で `/aws/lambda/trade-agent-prod-tick` の最後のエラーを見る
2. 建玉があるなら、bitbank の画面から手動で決済するか損切り注文を置く
3. Lambda の同時実行数上限、IAM 権限、DynamoDB スロットリングを確認
4. 復旧後、`trade-agent tick` を1回手動実行して整合を取る

### 「取引所APIの連続失敗」

Private API が3回連続で失敗。口座状態が確認できないため新規建ては自動停止済み。

1. bitbank のステータスページと `GET /v1/spot/status` を確認
2. APIキーが失効・削除されていないか確認
3. レート制限(HTTP 429)なら `exchange.rate_limit` を下げる
4. 復旧すると失敗カウンタは自動的に 0 に戻る

### 「取引所側の損切り注文を出せませんでした」

`stop` 注文が拒否された(取引所側でストップ注文が一時停止、
または発注時点で既に損切り水準を割っていた)。ローカル監視に切り替え済み。

**この状態では tick が止まると損切りも止まる。**

1. `get_status` で建玉と `protection` を確認
2. bitbank のステータスとメンテナンス告知を確認
3. tick のハートビートアラームが `OK` であることを確認する(最優先)
4. 復旧すれば次のサイクルから自動的に取引所側へ戻る

### 「取引所側の損切り注文が消えました」

損切り脚が REJECTED / CANCELED になった。ローカル監視へ自動的に切り替わり、
建玉は保有したまま。上と同じ確認をする。

### 「利確注文を取り消せず、損切りが機能しない可能性があります」

**最優先。** 取引所が損切りの残高確保をトリガー時まで遅延させる挙動で、かつ
利確の指値売りが残ってしまった状態。この場合、**損切りは発動時に残高不足で
拒否される** — 注文一覧上は保護されて見えるのに実際は無保護。

1. bitbank の注文一覧を開く
2. **利確の指値売り注文を手動で取り消す**
3. 損切りの `stop` 注文が残っていることを確認する
4. 残っていなければ手動で損切り注文を出すか、建玉を決済する

### 「OCO の残注文を取り消せませんでした」

片方が約定したのに、もう一方を取り消せなかった。取引所側に決済注文が
残っている可能性がある。

1. bitbank の注文一覧を確認
2. 残っていれば手動で取り消す(建玉はもう無いので、約定すると
   持っていないBTCを売ろうとして失敗するか、意図しない売り建てになる)

### 「OCO で建玉より多く売却しました」

値が飛んで両脚とも約定した場合など。現物では起きないはずの状態。

1. bitbank の残高と約定履歴を突き合わせる
2. `get_trades` の記帳(加重平均で記録されている)と照合する

### 「pending order could not be reconciled」

`pending` 行に対応する注文が取引所側に見つからない。**再発注はしていない。**

1. bitbank の注文履歴を該当時刻の前後で確認
2. 注文が存在する → その注文を手動で扱う(または放置して SL/TP を手動管理)
3. 注文が存在しない → 発注は届かなかった。`orders` テーブルの
   該当行が `UNKNOWN` のままでよい。次サイクルは通常どおり動く

**やってはいけないこと:** 「たぶん届いていないから」と手動で同じ注文を出すこと。
二重建玉になる。

### 「月次LLM予算上限に到達」

当月の LLM 呼び出しを停止した。**5分tickと損切り監視は動いている。**
翌月1日(JST)に自動的にリセットされる。

前倒しで再開したい場合は `cost.total_budget_jpy` を引き上げて再デプロイする。
総額3,000円の制約を動かすことになるので、オーナーの判断事項。

## 状況を調べる

Claude のチャット(カスタムコネクタ経由)から:

- 「今の状況は?」 → `get_status`
- 「昨日のレポートを見せて」 → `get_daily_report`
- 「直近1週間の約定は?」 → `get_trades`(probe は分けて集計される)
- 「あのトレードはなぜ入ったの?」 → `get_agent_log`(3案・批判・裁定・検査が全部残っている)
- 「今までの教訓は?」 → `get_lessons`

ローカルからも同じものが読める:

```bash
PYTHONPATH=src python -m trade_agent.cli status
PYTHONPATH=src python -m trade_agent.cli mcp get_trades --args '{"days":7}'
```

## よくある状態と、それが正常な理由

### 何日も取引していない

正常。合意ルール(3案中2案以上が buy)は簡単には成立しない。
72時間に達すると3日ルールが最小ロットの偵察トレードを1回入れる。

ただし次の場合は3日ルールも発火しない(すべて仕様どおり):
キルスイッチ、連敗ブレーキ、日次損失上限、急変動停止、オーナー pause、
probe の月間損失上限到達、建玉保有中。

`get_status` の `boredom_rule` と `safety` を見れば理由が分かる。

### `no_trade` が続く

`get_agent_log` で `judge` の `rationale` を読む。よくある理由:

- 買い提案が2件に届かなかった
- 利確幅が往復手数料を上回らなかった(ガードが棄却)
- 損切り幅が広すぎて、最小ロットでも1トレードリスク上限を超えた
  (この口座規模では珍しくない)

### `protection` が `exchange_stop_only` のまま

**これが現物での正常な状態。** 損切りが取引所側、利確がローカル評価。
現物残高は売り注文1つしか裏付けられないため、両脚が同時に載ることはない。
`exchange_oco`(両脚とも取引所側)になるのは、取引所が両方の残高を
確保できる場合だけ。

### `cache_read_tokens` がずっと 0

想定内。`claude-haiku-4-5` の最小キャッシュ長 4,096 トークンに対して
共通プレフィックスが約2,000トークンしかない。
判断の選択肢は docs/OPEN-QUESTIONS.md A-4。

### 予算の消化が想定より速い

1. `get_status` の `cost` で消化率を確認
2. `agent_calls` テーブルで、どのエージェントの `retries` が多いか調べる
   → 差し戻しが多いエージェントのプロンプトを調整する
3. 支出は日割りでペース配分される。使いすぎた日の翌日は取り分が自動的に縮むので、
   放置しても月間予算は破られない
4. それでも速いなら `cost.daily_allowance_multiplier` を下げる(既定 2.0 =
   均等ペースの2倍まで1日で使ってよい)

## 手動操作

```bash
# 1サイクルだけ回す(オフライン、実発注なし)
PYTHONPATH=src python -m trade_agent.cli --local decide

# 本番構成で1サイクル(paper_trading=true なら実発注はされない)
PYTHONPATH=src python -m trade_agent.cli decide --trigger manual

# 特定サイクルの再実行 → 何も起きないのが正しい(冪等)
PYTHONPATH=src python -m trade_agent.cli decide --cycle-id cyc-20260302T090000Z-floor
```

## エスカレーション判断

| 事象 | 自動で回復するか | 人間の介入 |
|---|---|---|
| 取引所の一時的な 5xx | する(指数バックオフ) | 不要 |
| レート制限 429 | する | 頻発するなら設定変更 |
| 連敗ブレーキ | する(24時間) | 不要 |
| 急変動停止 | する(1時間) | 不要 |
| 日次損失上限 | する(JST 翌日) | 原因の確認は推奨 |
| LLM 予算上限 | する(翌月) | 予算見直しの判断 |
| 損切り脚の発注失敗 | する(次サイクルで再試行) | tickの生存確認は必須 |
| キルスイッチ | **しない** | **必須** |
| 利確脚を取り消せない | **しない** | **必須・最優先**(損切りが無効化される) |
| 突合不能な pending 注文 | **しない** | **必須** |
| tick ハートビート断 | **しない** | **必須・最優先** |
