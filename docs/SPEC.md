## 1. 概要

### 1.1 目的

bitbank の現物取引所で、統計・機械学習モデルの判断に基づいて自動売買するエージェントを開発する。

### 1.2 スコープ

- 対象: 現物の JPY 建てペア。ポジションは「暗号資産を保有」か「円で待機」の2状態のみ（ロングまたはフラット）。
- 対象外: 信用取引、出金 API、数秒〜数分単位の高頻度取引、販売所。

### 1.3 現在の状態

- Phase 1（`bbdata`）: 実装済み。Phase 0 で実 API での動作を確認した。
- Phase 0: V1〜V5 を GitHub Actions 上で実施し、結果を §9 に記録した（V6 は Phase 7 で実施）。
- Phase 2〜6（`bbresearch`）: 実装済み。単体テストは合成データで通過。実データでの結果は `reports/research/report.md`（GitHub Actions の `research` ワークフローが書き込む）。
- 実 API へのアクセスは GitHub Actions 上で行う（`.github/workflows/`）。開発環境からは行わない。
- Phase 6 の初回結果（2026-09-23、run 35897632078、§7 の初期値のまま）: 一次シグナルだけでは開発期間・ホールドアウトとも大きく負け、ランダムエントリーと同程度。メタモデルの AUC は 0.53〜0.57 で、損失は減るが手数料込みでプラスにはならない（DSR はほぼ 0）。詳細は `reports/research/report.md`。
- パラメータ探索（2026-09-23、run 35912978259、768 通り）: 一次シグナルのみで手数料込みプラスの組み合わせは 0 / 1,536。探索の前に決めた基準で `dip/threshold_0.6/lgbm`（k_h=4, k_up=3, k_dn=4, N_v=16, delta=0.1%, T_fill=15分）を選択。開発期間は取引 899 件・+123%・シャープ 0.55 だが DSR ≈ 0（試行 1,650）。
- ホールドアウトでの1回だけの評価（2026-09-23、run 35917266777）: 選択した戦略は取引 19 件・+4.9%・勝率 57.9%（11/19）。件数が少なく偶然と区別できない。同期間のバイ・アンド・ホールドは +19.5%、一次シグナルのみは −18.6%（ランダムエントリーは平均 −18.7%）。メタモデルの AUC は 0.535。このホールドアウトはこれで使用済みとし、以後の選択の評価には使わない。
- 価格帯別出来高・TPO（run 35918054394）と収益率の分布の特徴量（run 35918572453）: メタモデルの AUC はほぼ変わらず（0.52〜0.56）。押し目のバックテストは改善したが DSR ≈ 0（試行 1,686）。
- 損失の要因分解（2026-09-23、run 35920060781、`reports/diagnose/report.md`、開発期間のみ）:
  1. 押し目イベント全体の事後リターンは小さいがプラス（4 本後 +0.035%、t = 5.4。§7 初期値）。順張りはほぼ 0。
  2. post_only 買い指値の約定は強い逆選択になっている。約定したイベントの 4 本後は −0.025%、約定しなかったイベントは +0.306%（D4）。

  4. 成行で必ず買うと逆選択はなくなるが、往復の費用が押し目の優位（+0.035〜0.06%）を大きく上回り −0.236%（D4）。
- 案 A（ホライズンの延長）の測定（2026-09-23、run 35920967121、`reports/diagnose/horizon.md`、開発期間のみ）: 押し目の優位（全体のドリフトを差し引いた超過リターン）は 15 分〜8 時間で +0.03〜0.04%（重ならないイベントでの t = 1.5〜3.5）、1 日以上ではマイナスに転じる。ホライズンを延ばすと費用込みの損益はプラスになるが、これは相場全体の上昇（ドリフト）を持っているだけで、シグナルの優位ではない。順張りは 1 日以上で超過リターンがプラス（+0.07〜0.3%）だが t ≈ 0 で有意でない。したがって、どのホライズンでもシグナルの優位は往復の費用（成行で約 0.3%）に届かない。
- 案 B（逆選択を減らすエントリー）の比較（2026-09-23、run 35922051561、`reports/diagnose/entry.md`、開発期間のみ、8 ルール × 2 組 × 2 シグナル）:
  - 下げ止まりを確認してから指値を出すルール（1・2・4 本待ち）は、かえって約定後の超過リターンが悪化した。
  - 終値より深い指値（0.5〜2σ 下）は逆選択を減らす。押し目・選択した組で、2σ 下の指値は約定率 16%、約定後 1 時間の超過リターン +0.10%（t = 2.5）、1σ 下は +0.05%（t = 2.5）。ただし 4 時間後には ≈ 0 に戻る。
  - 費用込みでは、約定後 4 時間で成行売りするとすべてマイナス（−0.10〜−0.17%）。現行のトリプルバリアでも最良が +0.002%（2σ 下、1,471 件）。

## 3. bitbank API 仕様の要点

出典は公式ドキュメント（<https://github.com/bitbankinc/bitbank-api-docs>、2026年9月に確認）。以下は設計に影響する点の要約です。実装時は必ず原文を参照してください。メンテナンスや API 変更の告知は <https://blog.bitbank.cc/tag/service> に掲載されます。

### 3.1 接続先

| 種別 | 接続先 | 認証 |
|---|---|---|
| Public REST | `https://public.bitbank.cc` | 不要 |
| Private REST | `https://api.bitbank.cc/v1` | 必要（`/spot/status` と `/spot/pairs` は不要） |
| Public Stream | Socket.IO。接続先とルーム名は `public-stream_JP.md` を参照 | 不要 |
| Private Stream | PubNub。`GET /user/subscribe` でチャンネル名とトークンを取得 | 必要 |

### 3.2 認証（Private REST）

ACCESS-TIME-WINDOW 方式を使う。ヘッダーは次の4つ。

| ヘッダー | 内容 |
|---|---|
| `ACCESS-KEY` | API キー |
| `ACCESS-SIGNATURE` | 署名（下記） |
| `ACCESS-REQUEST-TIME` | UTC の UNIX 時刻（ミリ秒） |
| `ACCESS-TIME-WINDOW` | リクエストの有効期間（ミリ秒）。未指定時は 5000、上限 60000。5000 以下を推奨 |

署名は API シークレットによる HMAC-SHA256 で、対象文字列は次のとおり。

- GET: `REQUEST-TIME + TIME-WINDOW + パス（/v1 を含む）+ クエリ文字列`
- POST: `REQUEST-TIME + TIME-WINDOW + リクエストボディの JSON 文字列`

POST では、署名に使った JSON 文字列と送信するボディを完全に一致させること（シリアライズは1回だけ行う）。サーバー時刻とのずれが大きいと拒否されるため、実行環境の時刻同期（NTP）が必要。

### 3.3 レート制限

| 対象 | 上限 | 超過時 |
|---|---|---|
| Private REST 取得系 | 10回/秒（ユーザーごと） | HTTP 429 |
| Private REST 更新系（新規注文・取消・出金） | 6回/秒（ユーザーごと） | HTTP 429 |
| Public REST | 【要検証】公式ドキュメントに数値の記載なし | — |

### 3.4 使用するエンドポイント

Public（認証不要）

| メソッド・パス | 用途 | 備考 |
|---|---|---|
| `GET /{pair}/transactions/{YYYYMMDD}` | 指定日の全約定 | 日付省略時は最新60件。日付境界のタイムゾーンは【要検証】 |
| `GET /{pair}/candlestick/{type}/{period}` | 公式ロウソク足 | 1min〜1hour は `YYYYMMDD`、4hour 以上は `YYYY`。`ohlcv` は `[始値, 高値, 安値, 終値, 出来高, UnixTimeミリ秒]` |

### 3.5 手数料

- 2026-09-23 に `/spot/pairs` で取得した btc_jpy の値: `maker_fee_rate_quote = 0`、`taker_fee_rate_quote = 0.001`、`maker_fee_rate_base = taker_fee_rate_base = 0`（§9 V0）。つまり現時点では **メイカー 0%、テイカー 0.1%**（quote 通貨で課金）で、メイカー報酬はない。
- 当初の記載（メイカー -0.02% の報酬、テイカー 0.12%）は、この API の値と一致しない。
- 実装では手数料率をハードコードせず、`/spot/pairs` の `maker_fee_rate_*` / `taker_fee_rate_*` を実行時に取得する（`bbresearch` は設定で上書きしない限りこの値を使う）。
- 過去期間のバックテストにも現在の手数料率を適用している。過去の手数料体系（キャンペーン等）は反映していない。
- 【要検証】手数料率の符号の規約（メイカー報酬が負の値で表されるか）と、手数料が base / quote のどちらで課されるか。少額の実取引で `trade_history` の `fee_amount_base` / `fee_amount_quote` を確認する。

### 3.6 設計上注意すべき仕様

1. サーキットブレイク中（`circuit_break_info.mode` が `NONE` 以外）は成行注文ができず、エラー 70020 になる。また、この間は `post_only` が `false` として扱われる。つまり CB 中の買い指値はテイカーとして約定し得る。
2. 注文種別は `limit`, `market`, `stop`, `stop_limit`, `take_profit`, `stop_loss`, `losscut` で、OCO はない。
3. 現物の発注中の数量は `locked_amount` としてロックされる。利確の売り指値を出したまま、同じ数量を成行で売ることはできない。先に利確指値を取り消す必要がある。
4. 3か月以上前の約定済み・取消済みの注文は API で取得できない。注文と約定の記録は自前で保存する。
5. 公式サポートによると、指値でも発注から板に載るまでの時間差でテイカーになる場合がある。メイカーを保証するには `post_only` を使う。
6. 【要検証】`post_only` 指値の価格が即時約定する水準だった場合の挙動（拒否されるのか、取消扱いになるのか）。
7. テスト環境（サンドボックス）は公式ドキュメントの一覧に記載がない。ペーパートレードは自前のドライランで行う（§5 Phase 7）。
8. API キーには出金権限を付けない。

### 4.2 データの流れ

5. 設定値はコードに埋め込まず、`configs/*.yaml` に置く。

### Phase 1: 過去データ基盤【実装済み】

使い方は `README.md` を参照。保存先は次のとおり。

```
data/raw/transactions/{pair}/{YYYYMMDD}.parquet   約定の生データ（1日1ファイル）
data/raw/candles/{pair}/{type}/{period}.parquet   公式ロウソク足（検証用）
data/bars/{pair}/{freq}.parquet                   集計済みの足
```

実装上の判断:

- 日付境界のタイムゾーンが不明なため、前後1日を余分に取得し、`transaction_id` で重複を除いてから `executed_at` で切り出す。
- 直近2日分は未確定の可能性があるため毎回取り直す。それより古い日付はファイルがあればスキップする。
- 約定のない足は、close を直前の足から前方埋めし（過去方向のみ）、OHLC と vwap を close にそろえる。

足の列定義:

| 列 | 定義 |
|---|---|
| `open`, `high`, `low`, `close` | 約定価格の OHLC |
| `volume`, `notional` | 出来高（base 通貨）、売買代金（quote 通貨） |
| `vwap` | `notional / volume`（約定なしの足は close） |
| `n_trades`, `n_buy`, `n_sell` | 約定件数と side 別件数 |
| `buy_volume`, `sell_volume` | side 別出来高 |
| `volume_imbalance` | `(buy_volume - sell_volume) / volume`（約定なしは 0） |
| `max_buy_price` | side=buy の約定の最高値（約定なしは NaN） |
| `min_sell_price` | side=sell の約定の最安値（約定なしは NaN） |
| `large_volume` | 数量が `large_trade_amount` 以上の約定の出来高（指定時のみ） |
| `is_empty` | 約定がなかった足 |

`large_trade_amount` は固定値で指定する。全期間の分位点などで決めると先読みになる。

### Phase 2: 一次シグナル（CUSUM フィルタ）

López de Prado『Advances in Financial Machine Learning』（2018）Snippet 2.4 の対称 CUSUM フィルタを基にする。

入力は15分足の `close`。各足 `t` について次を計算する。

```
r_t   = ln(close_t / close_{t-1})          約定なしの足では 0
σ_t   = r の EWMA 標準偏差（span = sigma_span、t までのデータのみ）
h_t   = k_h × σ_t
S⁺_t  = max(0, S⁺_{t-1} + r_t)
S⁻_t  = min(0, S⁻_{t-1} + r_t)

S⁻_t ≤ -h_t なら signal_type = "dip"（押し目）のイベントを出し、S⁻ を 0 に戻す
S⁺_t ≥  h_t なら signal_type = "breakout"（順張り）のイベントを出し、S⁺ を 0 に戻す
```

原典の定式化では期待リターンを差し引くが、15分足では期待値を 0 とみなす（この扱いは前提として明記しておく）。

出力（events テーブル）:

| 列 | 内容 |
|---|---|
| `event_id` | 一意な ID |
| `pair` | 通貨ペア |
| `t0` | 判断時刻（イベント足の終了時刻） |
| `signal_type` | `dip` / `breakout` |
| `s_value` | 閾値を超えたときの `S⁺` または `S⁻` |
| `h`, `sigma` | そのときの閾値と σ |

テスト:

- 合成系列で、想定どおりの回数と時刻にイベントが出る。
- 先読みがない。系列の末尾に将来の足を追加しても、過去のイベントが変わらない。

### Phase 3: 約定考慮トリプルバリア

イベントごとに、post_only 買い指値を出した場合の約定と決済を、約定単位のデータで再現する。

入力: events、約定の生データ、15分足、ペア仕様（呼値・手数料率）。

手順:

1. **エントリー価格**: `P_e = close(t0) × (1 − δ)` を呼値に合わせて切り捨てる。本番では post_only が約定側の価格にならないよう、`min(P_e, 最良買気配)` を使う。過去の最良気配は取得できないため、研究時と本番時でこの点に差が出る。その影響は Phase 7 のドライランで測る。
2. **約定判定**: `[t0, t0 + T_fill)` の約定を時刻順に調べ、`side == "sell"` かつ `price < P_e` の約定が初めて現れた時刻を約定時刻 `t_f` とする（`fill_rule = strict`）。キュー位置が分からないため、同値の約定は約定とみなさない。比較用に同値を含める `fill_rule = touch` も実装する。約定がなければ「未約定」として記録し、決済のシミュレーションは行わない。
3. **バリア設定**: `σ_0` は `t0` 時点の σ とする。
   - 上側 `U = P_e × (1 + k_up × σ_0)`（呼値に合わせて切り上げ）
   - 下側 `L = P_e × (1 − k_dn × σ_0)`
   - 時間切れ `t_v = t_f + N_v × 15分`
4. **決済判定**: `t_f` より後の約定を時刻順に調べ、最初に該当した条件で決済する。
   - 利確: `side == "buy"` かつ `price > U`。決済価格は `U`、メイカー。
   - 損切り: `price ≤ L`（side は問わない）。決済価格は `その約定価格 × (1 − s_slip)`、テイカー。
   - 時間切れ: `t_v` に達した。決済価格は `t_v 直前の約定価格 × (1 − s_slip)`、テイカー。
5. **手数料込みリターン**: `f_e`, `f_x` はエントリー・決済の手数料率（メイカー報酬は負の値として扱う。符号の規約は §3.5 の要検証事項に従って確定させる）。

   ```
   ret_net = (P_x × (1 − f_x) − P_e × (1 + f_e)) / (P_e × (1 + f_e))
   ```

6. **ラベル**: `ret_net > 0` なら `y = 1`、それ以外は `y = 0`。

出力（labels テーブル）: `event_id`, `filled`, `t_f`, `P_e`, `U`, `L`, `t_v`, `exit_type`（`tp` / `sl` / `time`）, `t_x`, `P_x`, `ret_net`, `y`, 使用したパラメータ一式。

前提と制約:

- 発注数量の全量が `P_e` で約定すると仮定している。この仮定は、発注量が出来高に対して十分小さい場合にしか成り立たない。
- 約定の検知から利確指値を出すまでの遅延は無視している。
- 本番の決済ロジック（Phase 7）と同じ判定関数を使えるように実装する。

テスト:

- 手作りの約定列で、利確・損切り・時間切れ・未約定の各ケースを確認する。
- `strict` と `touch` の違いを確認する。
- σ に `t0` より後のデータが使われていないことを確認する。

### Phase 4: 特徴量

すべて開始時刻が `t0` より前の足から計算する。ローリング計算は、窓が満たない区間を NaN とする（`min_periods = 窓長`）。

| 特徴量 | 定義 |
|---|---|
| `ret_k` | 直近 k 本の対数リターン（k = 1, 4, 16, 96） |
| `rv_k` | 直近 k 本の `r` の標準偏差（k = 16, 96） |
| `pk_vol_k` | Parkinson ボラティリティ `sqrt(mean(ln(high/low)²) / (4 ln 2))`（k = 16, 96） |
| `vol_z` | log(volume) の直近96本に対する z スコア |
| `imb_k` | 直近 k 本の `Σ(buy_volume − sell_volume) / Σ volume`（k = 4, 16） |
| `ntrades_z` | 約定件数の直近96本に対する z スコア |
| `large_share_k` | 直近 k 本の `Σ large_volume / Σ volume` |
| `empty_share` | 直近96本に占める約定なしの足の割合 |
| `dist_ma_n` | `(close − SMA_n) / (σ × close)`（n = 16, 96） |
| `cusum_ratio` | `|s_value| / h` |
| `sigma` | `t0` 時点の σ |
| `hour_sin`, `hour_cos`, `dow_sin`, `dow_cos` | 時刻・曜日の周期エンコード |

線形モデルで標準化が必要な場合は、学習側の fold だけで平均と分散を推定する。

#### 価格帯別出来高・TPO（2026-09-23 追加、オーナー提案）

`bbresearch/profile.py`。設定 `features.profile: true` で有効になる。判断時刻 t0 の直前 24 時間 `[t0 − 24h, t0)` だけから作る（オーナー決定）。価格帯の刻みは `0.25 × σ_0 × close(t0)`（σ に比例、オーナー決定）で、境界は close(t0) に揃える。距離はすべて σ 単位。

| 特徴量 | 定義 |
|---|---|
| `vp_poc_dist`, `tpo_poc_dist` | 出来高（TPO）が最も多い価格帯の中心と close の距離 |
| `vp_vah_dist`, `vp_val_dist`（tpo も同様） | バリューエリア（POC から隣の多い側へ広げ、全体の 70% に達するまで）の上端・下端と close の距離 |
| `vp_va_pos`, `tpo_va_pos` | バリューエリア内での close の位置（下端 0、上端 1） |
| `vp_at_price`, `tpo_at_price` | close の価格帯の量 ÷ 量のある価格帯の平均 |
| `vp_to_upper`, `vp_to_lower`（tpo も同様） | close から利確バリア U まで、損切りバリア L から close までの価格帯の量が全体に占める割合 |
| `vp_skew` | 出来高で重み付けした価格の歪度 |
| `tpo_single_up`, `tpo_single_dn` | close から U まで、L から close までの価格帯のうち TPO が 1 以下の割合 |

TPO は 15 分足を t0 から過去へ 2 本ずつまとめた 30 分区間で数える（Market Profile の慣例）。仮説は「出来高の厚い価格帯では値動きが止まりやすく、薄い価格帯は抜けやすい。したがって U・L までの間の出来高の分布は、どちらのバリアに先に届くかの予測に役立つ」。有効かどうかは検証で判断する。

#### 収益率の分布のパラメータとその変化（2026-09-23 追加、オーナー提案）

`bbresearch/distfeat.py`。設定 `features.dist: true` で有効になる。メタモデルの特徴量として使い、一次シグナル（D6）は変えない（オーナー決定）。分布は正規分布と t 分布、窓は 4・16・96 本（オーナー決定）。

| 特徴量 | 定義 |
|---|---|
| `dist_mu_t_k` | 平均の t 値 μ̂_k / (σ̂_k / √k) |
| `dist_dmu_t_k` | 直近 k 本と直前の k 本（重ならない区間）の平均の差 ÷ その標準誤差 |
| `dist_dlogsd_k` | 同じ2区間の標準偏差の対数比 |
| `dist_tdf_k`, `dist_dlogtdf_k` | t 分布の自由度（尖度からのモーメント推定 ν = 4 + 6/超過尖度、上限 100）とその対数比（k = 16, 96） |
| `dist_pup_k` | ドリフト μ̂_k・分散 σ̂_k² のブラウン運動が、利確バリアに損切りバリアより先に届く確率（時間切れは考慮しない。k = 16, 96） |

平均の変化を t 値で表すのは、平均の推定誤差（σ/√k）が平均そのものよりはるかに大きく、差の大きさをそのまま使うと雑音になるため。

### Phase 5: メタモデル

**学習データ**: Phase 3 で約定したイベントのみを使う。発注の期待値は `P(約定) × E[損益 | 約定]` であり、未約定なら損益は 0 になる。したがって発注すべきかどうかは `E[損益 | 約定]` の符号で決まり、約定したイベントだけで学習すれば足りる。未約定イベントは約定率の分析に使う。

**モデル**: 【確定】D6 に従い、`dip` と `breakout` で別々のモデルを学習して比較する。

- ベースライン: ロジスティック回帰
- 主モデル: 勾配ブースティング（LightGBM など）

**サンプル重み**: ラベル期間 `[t_f, t_x]` の重なりから平均ユニークネスを計算して重みにする（同書 4.4 節）。

**交差検証**: Purged K-fold（同書 7 章）。テスト側のラベル期間 `[t0, t_x]` と重なる学習サンプルを除外し、各テスト区間の直後にエンバーゴ期間（初期値 `N_v` 本分）を設ける。

**ホールドアウト**: 直近の一定期間はモデル選択に一切使わない。期間の長さは【未決】U5。

**評価指標**: log loss、AUC、しきい値ごとの precision / recall、確率の較正。最終判断は Phase 6 のバックテストで行う。

**成果物**: モデルファイルと、次のメタデータを一緒に保存して再現できるようにする。特徴量一覧、パラメータのハッシュ、学習期間、データのバージョン、`signal_type`。

### Phase 6: バックテスト

約定の生データ上でイベント駆動のシミュレーションを行う。約定・決済の判定には Phase 3 と同じ関数を使う。

ルール:

1. ペアごとに同時に持てるポジションは1つ。エントリー注文の待機中またはポジション保有中は、新しいイベントを無視する。
2. 発注量はメタモデルの予測確率から決める（同書 10.3 節の方式）。比較用に、`p ≥ θ` のとき固定額で発注するしきい値方式も実装する。
3. 発注量が `max(unit_amount, min_amount)` 未満なら発注しない。

レポートに含める項目:

- 手数料込みの累積リターン、取引回数、約定率、勝率、平均利益・平均損失、最大ドローダウン、シャープレシオ、保有時間の割合、手数料の内訳（メイカー報酬とテイカー手数料）
- `exit_type` ごとの件数と損益

比較対象:

- メタモデルなし（一次シグナルのみ）
- バイ・アンド・ホールド
- 同じ頻度のランダムエントリー

過学習の管理: 試行したパラメータの組み合わせ数を実験ログに記録し、多重検定を考慮した評価（例: Deflated Sharpe Ratio）を行う。ウォークフォワードでの再学習頻度は【未決】U5。

### ルール A: 価格帯別出来高の VAL での反発（`bbresearch/val_rule.py`、2026-09-24）

TPO・価格帯別出来高から直接売買を決めるルールベースの方式（オーナー提案）。4 つの候補のうちルール A だけを検証する（オーナー決定）。数値は検証前にオーナーと合意して固定した（`configs/val_rule.yaml`）。

- 1 分ごとに直近 24 時間の価格帯別出来高（刻み 0.25σ、バリューエリア 70%）を作る。
- ポジションも注文もなく、現在値がバリューエリア内にあり、POC − VAL ≥ VAL × 0.3% なら、VAL に post_only 買い指値（60 分有効）。
- 利確は約定時点の POC に post_only 売り指値、損切りは VAL − 0.5 × (POC − VAL) で成行、時間切れは 4 時間後に指値（15 分で成行に切り替え）。
- 全期間（2017-02-14 〜 2026-09-22）で 1 回だけ評価し、年ごとの成績と、同じ時刻に VAL と無関係な深さで指値を出した比較対象を並べる。良ければ、発注しないドライランで前向きに確かめる（オーナー決定）。
- 1 分ごとの計算は評価期間で最大約 505 万回（3,506 日 × 1,440 分）。注文中・保有中は読み飛ばすので実際はそれより少ない。

### 15 分後の上げ下げの予測: 二段構えのモデル（`bbresearch/direction.py`、2026-09-25）

TPO・価格帯別出来高を含む特徴量から、15 分後に上がるか下がるかを予測する（オーナー提案）。オーナー決定: ホライズン 15 分、特徴量は全部、二段構え、学習 2017〜2023 年・評価 2024-01〜2026-09 で1回、A 単独と A+B を比べる。

- 正解: 時刻 t の直前の約定価格と t + 15 分の直前の約定価格を比べ、上がれば 1、下がれば 0。同じなら除く。
- 特徴量（どれも t より前のデータだけ）:
  - 1 分足: 直近 1・5・15・60 分の対数リターン、1・5・15 分の出来高（log1p）・売買の偏り（(買い − 売り) / 出来高）・約定件数
  - 15 分足（t 以前に確定した最新の足）: `features.bar_features` と `distfeat.dist_bar_features`（接頭辞 `b_`）
  - 価格帯別出来高（直近 24 時間の約定、刻み 0.25σ、σ は確定済みの最新の足の EWM σ）: POC・VAH・VAL までの距離（σ 単位）、バリューエリア内の位置、現在の価格帯の厚さ（出来高のある価格帯の平均に対する比）、上下 1σ 以内の出来高の割合、歪度
  - TPO（直近 96 本を 30 分の区間 48 個にまとめる）: 同じ水準の距離・位置・厚さ・割合と、上下 1σ 以内でシングルプリント（1 区間だけ）の価格帯の割合
  - 時刻・曜日（sin/cos）
- モデル B: 1 分ごとの全時刻で LightGBM（300 本、学習率 0.05、葉 31）。学習期間は Purged K-fold（5 分割、エンバーゴ 15 分）の out-of-fold 予測、評価期間は学習期間全体で学習したモデルの予測。
- モデル A: 15 分の区切りの時刻だけで同じ LightGBM。A+B は A の特徴量に直近 15 分（t − 14 分〜t）の B の予測の平均・最新・変化・ばらつきを加える。学習期間の A+B の交差検証の値は、B の out-of-fold 予測を使っても多少楽観的になりうる。比較は評価期間で行う。
- 評価期間の指標: AUC・log loss、A+B と A の AUC の差（日単位ブロック・ブートストラップ 200 回）、確率がしきい値（0.55・0.6）以上で買い 15 分後に売った場合の損益（成行往復と、手数料・滑りなしの上限）。
- 評価期間の一部（2024-01〜2026-03）は maker 決済の確認で使っている。完全に未使用のデータではない。

#### 1 時間版（`configs/direction_1h.yaml`、2026-09-26 オーナー指示）

15 分では値幅が費用に届かなかったため、最終のエントリー判断を 1 時間ごとにする（売買は多くても 1 時間に 1 回）。判断には 1 分ごとの TPO×価格帯別出来高のシグナルの直近 60 分の推移を使う。オーナー決定: シグナルは B の上げ確率と生の水準の両方、特徴量は全部、推移は要約した数値で渡す、決済は 1 時間後に売る。

- ホライズン h = 60 分（`horizon_min`）。B は 1 分ごとに「60 分後に上がるか」を予測し、A は毎正時に判断する。エンバーゴも 60 分。
- A+B: A の特徴量 + 直近 60 分の B の予測の平均・最新・変化・ばらつき・直近 15 分の平均。
- A+B+L（`level_summary: true`）: さらに、直近 60 分の生の価格帯別出来高・TPO の 17 水準それぞれの平均と変化（最新 − 60 分前）。
- 比較は A・A+B・A+B+L の 3 つ。AUC の差はいずれも A に対して測る。

#### 目的変数を「費用を超える値幅で上がるか」にした版（`configs/direction_cost.yaml`、`direction_1h_cost.yaml`、2026-09-26 オーナー指示）

上げ下げの予測は当たっても値幅が費用に届かなかったため、目的変数を y = 1 if r > c（c は成行往復の損益ゼロに必要な対数リターン。テイカー 0.1%・滑り 0.05% から約 0.30%）に変える。オーナー決定: しきい値は成行往復の費用、ホライズンは 15 分と 1 時間の両方。
- `target_min_return: taker_round_trip`（手数料・滑りから計算）。数値を書けばその対数リターン。
- 正解が偏る（1 が少ない）ので、損益は固定のしきい値（0.3・0.4）に加え、評価期間の予測確率の上位 10%・5%（順位で選ぶ）でも出す。上位割合のしきい値は評価期間で決めているので、説明用。
- ワークフロー `direction_cost.yml` が 15 分版と 1 時間版を順に実行する。
- 両側版（`two_sided: true`、2026-09-26 オーナー指示）: 下げ側 y = 1 if r < −c も同じ特徴量で学習し、信号 = P(上げ > c) − P(下げ > c) を同じ変種どうしで作る。上げ確率と下げ確率の相関、信号がしきい値（0.05・0.1・0.2）以上または上位 10%・5% で買った損益、信号が最も低い側の値動きの平均（空売りはしないので参考）を出す。上げ側の結果が「大きく動くか」を当てているだけなら、相関が高く、差で買っても損益は改善しない。

### ボラティリティを抑えるポートフォリオ（`bbresearch/portfolio.py`、`scripts/portfolio.py`、2026-09-27 オーナー指示）

bitbank の JPY ペアで、組み合わせ最適化により分散を抑えたポートフォリオを組む。オーナー決定: 目標リターン付きの最小分散、銘柄数の上限（5）を決めて組み合わせを探索、日足・毎月再計算の前向き検証。

#### JPY 比率の日次調整（ボラ予測）（`bbresearch/volforecast.py`、`scripts/vol_daily.py`、`vol_daily.yml`、2026-09-27 オーナー決定）

### スイング（4 時間足・1〜3 日保有）の方向の研究（`bbresearch/swing.py`、`scripts/swing.py`、`swing.yml`、2026-09-28 オーナー決定）

オーナー決定（2026-09-28）: 方向の予測を短い時間軸で打ち切らず、スイングで続ける。4 時間足で判断し 1〜3 日保有する（D3 の変更）。最初に検証する仮説はトレンド（時系列モメンタム）と急落後の反発。数値は事前に固定し、全期間で 1 回だけ評価する。取引の範囲は現物の複数ペア（U1 の変更）。

- 根拠: 往復の費用 0.3% は、BTC の値動きの標準偏差（2022〜2026 年の年率 50%）に対して 4 時間で 28%、1 日で 11%、1 週間で 4%。文献（実在と内容を確認済み）: 暗号資産の時系列モメンタムと注目度による予測（Liu & Tsyvinski 2021, *Review of Financial Studies* 34(6)）、価格と移動平均の比による BTC の日次リターンの予測（Detzel, Liu, Strauss, Zhou & Zhu 2021, *Financial Management* 50(1)）、市場・規模・モメンタムの 3 因子（Liu, Tsyvinski & Wu 2022, *Journal of Finance* 77(2)）、モメンタムをボラで調整すると暴落が消えシャープがほぼ倍（Barroso & Santa-Clara 2015, *Journal of Financial Economics* 116(1)）。このリポジトリでも、200 日線のトレンドフィルタでポートフォリオのシャープが 0.72 → 1.12（ただし 16 通りから選んだ結果）。

### 分布推定の先行研究の調査（2026-09-28、オーナー指示）

オーナー指示（2026-09-28）: 期待収益率の分布推定の線で研究を進めるため、先行研究を調べる。範囲は、分布推定の手法、分布予測の評価法、暗号資産の予測可能性、分布予測の経済的な価値、向きの情報源（板・約定、取引所間、資金調達率、注目度・オンチェーン）。目的は、次に試す手法と評価の設計を決めること。全文（文献ごとの内容と URL、確認できなかった文献）は Notion のページ「先行研究の調査: 期待収益率の分布推定」（https://app.notion.com/p/3e9036495bee81d2971cfbe20a527d17）と、その下の付録 A〜E にある。

- 要点:
  - 文献の結論は、これまでの結果と同じ。分布の幅（ボラ）は予測できるが、中心（向き）は予測しにくい。符号の予測可能性の多くはボラの変動から生じる（Christoffersen & Diebold 2006, Management Science）。P(収益率 > 0.3%) の AUC 0.60 は、幅だけが変わる分布の式で説明できる。
  - 1 時間以下の向きは 2021〜2026 年のデータでも統計的には残るが、1 回の粗利は 0.5〜1.3 bp で、往復 30 bp に届かない（Kitron & Wengrowicz 2026、Kim & Hansen 2026。いずれも arXiv）。
  - 比較の基準が弱かった。暗号資産のボラの分位点では、ボラの単純な予測 × 標準化残差の分位点が、分位点回帰フォレストを使う方法と同等以上（Dudek, Orzeszko & Fiszeder 2025, arXiv 2508.15922）。HAR・GARCH-t を基準に加え、向きは「ボラだけのモデル」と「位置を固定した基準」に対する上乗せで測る。
  - テクニカル指標以外の向きの情報源（デリバティブの偏りの極端な状態、JPY の内外価格差、米国の現物 ETF の資金流出入、15 分境界の注文の偏り）は、どれも費用込みで 0.3% を超える強い証拠ではない。最大の報告は、資金調達率が極端に負になった後の 24 時間の平均 +0.506%（費用前、報告 1 本、掲載誌の水準は低い）。
  - 日次の JPY 調整の悪化は、文献から予想できる。ボラ管理で配分が良くなるには、高ボラの後に期待リターンが上がらない、下げでボラが上がる、費用が小さい、の 3 つが要る（Moreira & Muir 2017、Harvey ほか 2018、Cederburg ほか 2020）。費用があるときは、売買しない範囲（往復 0.3% で暗号資産の比率 ±5 ポイント前後）と部分調整が理論の答え（Guasoni & Muhle-Karbe 2012、Gârleanu & Pedersen 2013）。
  - 評価: 4 時間先を 1 時間ごとに出す予測では損失差の自己相関が強く、ラグ 3 までの HAC による DM 検定はサイズがゆがむ。fixed-b・EWC・ブロック・ブートストラップを使う（Shin & Schor 2026、Coroneo & Iacone 2025）。費用の水準では、予測平均の初等スコア（θ = 0.3%）の差が「予測平均が費用を超えたら買う」規則の費用控除後の損益の差と一致する（Ehm ほか 2016 の式から導いた）。費用付近の精度は twCRPS で測る（既存の `crps_weighted` に変換した値を渡せば計算できる）。2024〜2026 年の評価期間はすでに何度も使ったので、確定的な評価は前向きの期間で行う（Diebold 2012）。

### 評価の土台（候補 1）: ボラだけの基準に対する幅と向き（`bbresearch/distbase.py`、`bbresearch/fcompare.py`、`bbresearch/nullsim.py`、`scripts/dist_base.py`、`dist_base.yml`、2026-09-28 オーナー決定）

  - 無条件、直近 168 本・720 本（これまでの基準）。
  - HAR 型: log(次の h 本の実現分散の和) を、log(直近 1・4・24・168 本の実現分散の平均) と時刻・曜日のダミーに OLS で回帰し、σ̂_t = exp(予測 / 2)。分布は σ̂_t × z（z は学習期間の y / σ̂ の経験分布。Dudek ほか 2025 の残差の方法）。実現分散は 1 時間ごとの 1 分の対数リターンの二乗和。

  - 符号と大きさ（Brou & Luger 2026 を応用）: 大きさは HAR 型（|z| の分位点 50 点 × σ̂_t）、符号は「指標と大きさ」から LightGBM で学習した P(y > 0 | |z|, x)。木の数は学習期間の末尾 20% で早期停止して決め、学習期間全体で学習し直す（木を 300 本に固定すると、向きの情報がない合成データでも P(>0) のブライアスコアが HAR 型より 4 時間で 0.016、24 時間で 0.043 悪くなった）。参照は HAR 型。

**7.2 判断ループ（15分ごと）**

1. 足の終了時刻から数秒待ち、遅れて届く約定を取り込む。
2. Public Stream で受信した約定から、`aggregate_trades` で最新の足を作る。受信の欠落があれば REST の約定履歴で補完する。
3. CUSUM を更新する。イベントがあれば特徴量を計算し、メタモデルで確率と発注量を求める。
4. 発注前チェック:
   - `/spot/status` が `HALT` でない。数量が `min_amount` 以上
   - `circuit_break_info.mode` が `NONE`（CB 中は post_only が無効になるため新規エントリーしない）
   - `/spot/pairs` の停止フラグ（`stop_order`, `stop_buy_order` など）が立っていない
   - 円残高の `free_amount` が足りる
   - リスク制限（7.4）に抵触しない
5. `min(P_e, 最良買気配)` で post_only 買い指値を出す。
6. `T_fill` 以内に約定しなければ取り消す。一部約定していれば、約定分をポジションとして扱う。
7. 約定したら（Private Stream の通知、または注文照会で確認）、約定数量で post_only 売り指値を `U` に出す。
8. Public Stream の約定を監視し、`price ≤ L` になるか `t_v` に達したら、利確指値を取り消す → 取消完了と `free_amount` を確認する → 成行で売る。
9. 判断内容、注文、約定、エラーをすべて記録する。

**7.3 注文の状態遷移**

| 現在の状態 | 事象 | 次の状態 | 処理 |
|---|---|---|---|
| `IDLE` | エントリー判断が出た | `ENTRY_PENDING` | post_only 買い指値を出す |
| `ENTRY_PENDING` | 全量が約定した | `POSITION_OPEN` | 約定数量で post_only 利確指値を出す |
| `ENTRY_PENDING` | `T_fill` 経過、未約定 | `IDLE` | 買い指値を取り消す |
| `ENTRY_PENDING` | `T_fill` 経過、一部約定 | `POSITION_OPEN` | 残りを取り消し、約定数量で利確指値を出す |
| `POSITION_OPEN` | 利確指値が全量約定した | `IDLE` | 記録する |
| `POSITION_OPEN` | 損切り条件または時間切れ | `EXITING` | 利確指値を取り消す |
| `EXITING` | 取消の完了と `free_amount` を確認した | `EXITING` | 残数量を成行で売る |
| `EXITING` | 成行売りが約定した | `IDLE` | 記録する |

異常時の扱い:

| 事象 | 対応 |
|---|---|
| post_only 指値が即時に拒否・取消された | そのイベントは見送る（挙動は §3.6-6 で要検証） |
| 利確指値の取消に失敗し、すでに約定していた | 利確で決済済みとして扱う |
| 利確指値が一部約定した後に損切り条件に達した | 残りを取り消し、残数量だけを成行で売る |
| 成行売りが 70020（CB 中）で拒否された | 【未決】U6 |
| Public Stream の切断 | バックオフ付きで再接続する。切断中は REST で補完する。データが一定時間更新されなければ新規エントリーを止める |
| Private Stream トークンの期限切れ（12時間） | `/user/subscribe` で再取得する。通知が途絶えている間は注文照会のポーリングで補う |
| HTTP 429 | バックオフする。更新系は毎秒6回を超えないように送信を制御する |
| プロセスの再起動 | `active_orders` と `assets` から状態を復元してから再開する |

**7.4 リスク管理**

次の項目を実装する。値はすべて【未決】U2。

- キルスイッチ（手動操作と、自動発動の両方）
- ペアごとの最大ポジション金額
- 1日の損失上限
- 連続損失回数の上限
- データ更新が途絶えたときの新規エントリー停止

**7.5 秘密情報**

API キーとシークレットは環境変数またはシークレット管理サービスから読み込む。ログには出力しない。リポジトリにはコミットしない。API キーには出金権限を付けない。

現状（2026-09-23）: GitHub Actions ではリポジトリの Secrets `bitbank_API`（API キー）と `bitbank_secret`（API シークレット）を環境変数 `BITBANK_API_KEY` / `BITBANK_API_SECRET` として渡す（`.github/workflows/auth-check.yml`）。既存システムは同じ口座のキーを AWS SSM Parameter Store（`/trade-agent/bitbank/*`）に置いている。作成時はリポジトリが公開だったので、ワークフローのログやコミットするレポートに残高・注文の内容を出さない方針にした（2026-09-27 に非公開へ切り替え、2026-09-28 に公開へ戻した。モニターの記録 `docs/monitor/` だけは公開のまま金額を残す。オーナー決定）。Secrets を使うワークフローは `push`（このリポジトリへの書き込み権限が必要）と `workflow_dispatch` だけで起動し、フォークからのプルリクエストでは起動しない。

既存システムと同じキー・同じ口座を使う。2026-09-23 時点で既存システムはペーパートレード（`paper_trading: true`、発注 API に到達しない設定）で、最後の tick は 2026-09-03 と稼働していないため、オーナーの判断でキーはそのまま使ってよい。既存システムを実取引で動かす場合は、同じ口座で2つのシステムが発注しないよう統合の設計（U7）で排他を決める。

**7.6 記録**

判断（特徴量、予測確率、モデルのバージョン）、注文のリクエストとレスポンス、約定、エラーを追記専用の形式で保存する。API からは3か月より前の注文を取得できないため、この記録が唯一の履歴になる。

**7.7 時刻同期**

ACCESS-REQUEST-TIME の検証があるため、実行環境を NTP で同期する。

## 11. 開発の進め方

4. 各フェーズで、テストの追加と、`README.md` および本書の更新を行う。
5. 実注文を出すコードは `dry-run` を既定にする。
6. 秘密情報をコミットしない。
7. 公開 API に大量のリクエストを送らない（レート制限の数値が不明なため）。
