## 1. 概要

### 1.1 目的

bitbank の現物取引所で、統計・機械学習モデルの判断に基づいて自動売買するエージェントを開発する。

### 1.2 スコープ

- 対象: 現物の JPY 建てペア。ポジションは「暗号資産を保有」か「円で待機」の2状態のみ（ロングまたはフラット）。
- 対象外: 信用取引、出金 API、数秒〜数分単位の高頻度取引、販売所。

### 1.3 現在の状態

Phase 1（過去データの取得と足の構築）を `bbdata` パッケージとして実装済み。単体テスト13件は HTTP をモックして通過している。実 API での動作は未確認（開発環境のネットワーク制限のため）。次の作業は Phase 0（実データ検証）。

## 3. bitbank API 仕様の要点

出典は公式ドキュメント（<https://github.com/bitbankinc/bitbank-api-docs>、2026年9月に確認）。以下は設計に影響する点の要約です。実装時は必ず原文を参照してください。メンテナンスや API 変更の告知は <https://blog.bitbank.cc/tag/service> に掲載されます。

### 3.1 接続先

| 種別 | 接続先 | 認証 |
|---|---|---|
| Public REST | `https://public.bitbank.cc` | 不要 |
| Private REST | `https://api.bitbank.cc/v1` | 必要（`/spot/status` と `/spot/pairs` は不要） |
| Public Stream | Socket.IO。接続先とルーム名は `public-stream_JP.md` を参照 | 不要 |
| Private Stream | PubNub。`GET /user/subscribe` でチャンネル名とトークンを取得 | 必要 |

### 3.2 認証（Private REST）

ACCESS-TIME-WINDOW 方式を使う。ヘッダーは次の4つ。

| ヘッダー | 内容 |
|---|---|
| `ACCESS-KEY` | API キー |
| `ACCESS-SIGNATURE` | 署名（下記） |
| `ACCESS-REQUEST-TIME` | UTC の UNIX 時刻（ミリ秒） |
| `ACCESS-TIME-WINDOW` | リクエストの有効期間（ミリ秒）。未指定時は 5000、上限 60000。5000 以下を推奨 |

署名は API シークレットによる HMAC-SHA256 で、対象文字列は次のとおり。

- GET: `REQUEST-TIME + TIME-WINDOW + パス（/v1 を含む）+ クエリ文字列`
- POST: `REQUEST-TIME + TIME-WINDOW + リクエストボディの JSON 文字列`

POST では、署名に使った JSON 文字列と送信するボディを完全に一致させること（シリアライズは1回だけ行う）。サーバー時刻とのずれが大きいと拒否されるため、実行環境の時刻同期（NTP）が必要。

### 3.3 レート制限

| 対象 | 上限 | 超過時 |
|---|---|---|
| Private REST 取得系 | 10回/秒（ユーザーごと） | HTTP 429 |
| Private REST 更新系（新規注文・取消・出金） | 6回/秒（ユーザーごと） | HTTP 429 |
| Public REST | 【要検証】公式ドキュメントに数値の記載なし | — |

### 3.4 使用するエンドポイント

Public（認証不要）

| メソッド・パス | 用途 | 備考 |
|---|---|---|
| `GET /{pair}/transactions/{YYYYMMDD}` | 指定日の全約定 | 日付省略時は最新60件。日付境界のタイムゾーンは【要検証】 |
| `GET /{pair}/candlestick/{type}/{period}` | 公式ロウソク足 | 1min〜1hour は `YYYYMMDD`、4hour 以上は `YYYY`。`ohlcv` は `[始値, 高値, 安値, 終値, 出来高, UnixTimeミリ秒]` |
| `GET /{pair}/depth` | 現在の板 | 上下各200件のスナップショットのみ。過去の板は取得できない |
| `GET /{pair}/ticker`, `GET /tickers_jpy` | 最良気配・最終価格 | |
| `GET /{pair}/circuit_break_info` | サーキットブレイク状態 | `mode`: `NONE` / `CIRCUIT_BREAK` / `FULL_RANGE_CIRCUIT_BREAK` / `RESUMPTION` / `LISTING` |
| `GET /v1/spot/status`（api.bitbank.cc） | 取引所の負荷状態 | `status`: `NORMAL` / `BUSY` / `VERY_BUSY` / `HALT`。`min_amount`（最小注文数量）は負荷が高いほど大きくなる |
| `GET /v1/spot/pairs`（api.bitbank.cc） | ペアの仕様 | 手数料率、`unit_amount`、`price_digits`、`amount_digits`、各種の注文停止フラグ |

Private（認証必要）

| メソッド・パス | 用途 | 備考 |
|---|---|---|
| `GET /user/assets` | 残高 | `free_amount`（利用可能）と `locked_amount`（発注中などでロック中） |
| `POST /user/spot/order` | 新規注文 | `pair`, `amount`, `price`, `side`, `type`, `post_only`, `trigger_price` |
| `GET /user/spot/order` | 注文照会 | |
| `POST /user/spot/orders_info` | 複数注文の照会 | POST メソッドである点に注意 |
| `GET /user/spot/active_orders` | 未約定注文の一覧 | 再起動時の状態復元に使う |
| `POST /user/spot/cancel_order` | 注文取消 | |
| `POST /user/spot/cancel_orders` | 複数注文の取消 | 最大30件 |
| `GET /user/spot/trade_history` | 自分の約定履歴 | `count` 最大1000。`maker_taker`、`fee_amount_base`、`fee_amount_quote` を含む |
| `GET /user/subscribe` | Private Stream の接続情報 | `pubnub_token` の有効期限は12時間。期限切れで切断されるため再取得が必要 |

### 3.5 手数料

- メイカー: 公式ページ（<https://bitbank.cc/about/trade>）によると、約定金額の 0.02% を受け取れる。
- テイカー: 0.12%（比較サイトの2026年8月時点の記載。一次情報では未確認）。
- 実装では手数料率をハードコードせず、`/spot/pairs` の `maker_fee_rate_*` / `taker_fee_rate_*` を実行時に取得する。
- 【要検証】手数料率の符号の規約（メイカー報酬が負の値で表されるか）と、手数料が base / quote のどちらで課されるか。少額の実取引で `trade_history` の `fee_amount_base` / `fee_amount_quote` を確認する。

### 3.6 設計上注意すべき仕様

1. サーキットブレイク中（`circuit_break_info.mode` が `NONE` 以外）は成行注文ができず、エラー 70020 になる。また、この間は `post_only` が `false` として扱われる。つまり CB 中の買い指値はテイカーとして約定し得る。
2. 注文種別は `limit`, `market`, `stop`, `stop_limit`, `take_profit`, `stop_loss`, `losscut` で、OCO はない。
3. 現物の発注中の数量は `locked_amount` としてロックされる。利確の売り指値を出したまま、同じ数量を成行で売ることはできない。先に利確指値を取り消す必要がある。
4. 3か月以上前の約定済み・取消済みの注文は API で取得できない。注文と約定の記録は自前で保存する。
5. 公式サポートによると、指値でも発注から板に載るまでの時間差でテイカーになる場合がある。メイカーを保証するには `post_only` を使う。
6. 【要検証】`post_only` 指値の価格が即時約定する水準だった場合の挙動（拒否されるのか、取消扱いになるのか）。
7. テスト環境（サンドボックス）は公式ドキュメントの一覧に記載がない。ペーパートレードは自前のドライランで行う（§5 Phase 7）。
8. API キーには出金権限を付けない。

### 4.2 データの流れ

研究時:

```
約定履歴(raw) → 15分足 → CUSUM イベント → 約定考慮トリプルバリア
  → 約定したイベントのみ抽出 → 特徴量＋ラベル → メタモデル → バックテスト
```

本番時:

```
Public Stream の約定 → 15分足 → CUSUM → 特徴量 → メタモデル推論 → 発注判断 → executor
```

学習時と本番時で、足の集計（`bbdata.bars.aggregate_trades`）と特徴量の計算には同じ関数を使うこと。別実装にすると、学習時と本番時で計算結果がずれる原因になる。

### 4.3 共通規約

1. 時刻は内部ですべて UTC で扱う。
2. 足の index は開始時刻。区間は左閉右開 `[t, t + 15分)`。
3. イベントの判断時刻 `t0` は、イベントが発生した足の終了時刻とする。`t0` の特徴量は開始時刻が `t0` より前の足だけから計算する（先読みの禁止）。
4. 価格と数量は `/spot/pairs` の `price_digits` / `amount_digits` に従って丸める。
5. 設定値はコードに埋め込まず、`configs/*.yaml` に置く。

## 5. フェーズ別仕様

### Phase 0: 実データ検証【最優先】

`bbdata` を実 API で動かし、次の前提を確認する。結果は §9 に追記する。

| ID | 確認事項 | 方法 | 完了条件 |
|---|---|---|---|
| V1 | 公式ロウソク足の timestamp の意味と、自前集計との一致 | BTC/JPY の直近7日で `download --candles 15min` と `validate` を実行 | `ohlc_match_rate` が最大になる `shift_bars` と、そのときの一致率・出来高誤差を記録。一致率が低い場合は原因を調べる |
| V2 | 約定の `side` がテイカー側の方向を表すか | `/depth` と `/transactions`（最新60件）を数分間同時に記録し、`buy` の約定価格が直前の売り気配以上、`sell` の約定価格が買い気配以下かを確認 | 前提が成り立つかを記録。成り立たない場合は `bars.py` の `max_buy_price` / `min_sell_price` と Phase 3 の約定判定を修正 |
| V3 | 約定履歴を何年前まで遡れるか | 日付を変えて少数のリクエストを送り、取得できる最古日を特定 | 最古日を記録 |
| V4 | Public REST のレート制限 | 通常の取得で 429 が返ったときの挙動を記録する。負荷試験はしない | 既定のリクエスト間隔（0.3秒）で問題がないかを記録 |
| V5 | 日付指定の約定取得の日付境界 | 各日ファイルの `executed_at` の最小値・最大値から判定 | タイムゾーンを記録（`bbdata` は前後1日を余分に取得するため、結果に関わらず動作する） |
| V6 | 手数料率の符号と課金通貨 | `/spot/pairs` の値と、少額の実取引の `trade_history` を比較 | Phase 7 の少額運用開始時に実施してよい |

### Phase 1: 過去データ基盤【実装済み】

使い方は `README.md` を参照。保存先は次のとおり。

```
data/raw/transactions/{pair}/{YYYYMMDD}.parquet   約定の生データ（1日1ファイル）
data/raw/candles/{pair}/{type}/{period}.parquet   公式ロウソク足（検証用）
data/bars/{pair}/{freq}.parquet                   集計済みの足
```

実装上の判断:

- 日付境界のタイムゾーンが不明なため、前後1日を余分に取得し、`transaction_id` で重複を除いてから `executed_at` で切り出す。
- 直近2日分は未確定の可能性があるため毎回取り直す。それより古い日付はファイルがあればスキップする。
- 約定のない足は、close を直前の足から前方埋めし（過去方向のみ）、OHLC と vwap を close にそろえる。

足の列定義:

| 列 | 定義 |
|---|---|
| `open`, `high`, `low`, `close` | 約定価格の OHLC |
| `volume`, `notional` | 出来高（base 通貨）、売買代金（quote 通貨） |
| `vwap` | `notional / volume`（約定なしの足は close） |
| `n_trades`, `n_buy`, `n_sell` | 約定件数と side 別件数 |
| `buy_volume`, `sell_volume` | side 別出来高 |
| `volume_imbalance` | `(buy_volume - sell_volume) / volume`（約定なしは 0） |
| `max_buy_price` | side=buy の約定の最高値（約定なしは NaN） |
| `min_sell_price` | side=sell の約定の最安値（約定なしは NaN） |
| `large_volume` | 数量が `large_trade_amount` 以上の約定の出来高（指定時のみ） |
| `is_empty` | 約定がなかった足 |

`large_trade_amount` は固定値で指定する。全期間の分位点などで決めると先読みになる。

### Phase 2: 一次シグナル（CUSUM フィルタ）

López de Prado『Advances in Financial Machine Learning』（2018）Snippet 2.4 の対称 CUSUM フィルタを基にする。

入力は15分足の `close`。各足 `t` について次を計算する。

```
r_t   = ln(close_t / close_{t-1})          約定なしの足では 0
σ_t   = r の EWMA 標準偏差（span = sigma_span、t までのデータのみ）
h_t   = k_h × σ_t
S⁺_t  = max(0, S⁺_{t-1} + r_t)
S⁻_t  = min(0, S⁻_{t-1} + r_t)

S⁻_t ≤ -h_t なら signal_type = "dip"（押し目）のイベントを出し、S⁻ を 0 に戻す
S⁺_t ≥  h_t なら signal_type = "breakout"（順張り）のイベントを出し、S⁺ を 0 に戻す
```

原典の定式化では期待リターンを差し引くが、15分足では期待値を 0 とみなす（この扱いは前提として明記しておく）。

出力（events テーブル）:

| 列 | 内容 |
|---|---|
| `event_id` | 一意な ID |
| `pair` | 通貨ペア |
| `t0` | 判断時刻（イベント足の終了時刻） |
| `signal_type` | `dip` / `breakout` |
| `s_value` | 閾値を超えたときの `S⁺` または `S⁻` |
| `h`, `sigma` | そのときの閾値と σ |

テスト:

- 合成系列で、想定どおりの回数と時刻にイベントが出る。
- 先読みがない。系列の末尾に将来の足を追加しても、過去のイベントが変わらない。

### Phase 3: 約定考慮トリプルバリア

イベントごとに、post_only 買い指値を出した場合の約定と決済を、約定単位のデータで再現する。

入力: events、約定の生データ、15分足、ペア仕様（呼値・手数料率）。

手順:

1. **エントリー価格**: `P_e = close(t0) × (1 − δ)` を呼値に合わせて切り捨てる。本番では post_only が約定側の価格にならないよう、`min(P_e, 最良買気配)` を使う。過去の最良気配は取得できないため、研究時と本番時でこの点に差が出る。その影響は Phase 7 のドライランで測る。
2. **約定判定**: `[t0, t0 + T_fill)` の約定を時刻順に調べ、`side == "sell"` かつ `price < P_e` の約定が初めて現れた時刻を約定時刻 `t_f` とする（`fill_rule = strict`）。キュー位置が分からないため、同値の約定は約定とみなさない。比較用に同値を含める `fill_rule = touch` も実装する。約定がなければ「未約定」として記録し、決済のシミュレーションは行わない。
3. **バリア設定**: `σ_0` は `t0` 時点の σ とする。
   - 上側 `U = P_e × (1 + k_up × σ_0)`（呼値に合わせて切り上げ）
   - 下側 `L = P_e × (1 − k_dn × σ_0)`
   - 時間切れ `t_v = t_f + N_v × 15分`
4. **決済判定**: `t_f` より後の約定を時刻順に調べ、最初に該当した条件で決済する。
   - 利確: `side == "buy"` かつ `price > U`。決済価格は `U`、メイカー。
   - 損切り: `price ≤ L`（side は問わない）。決済価格は `その約定価格 × (1 − s_slip)`、テイカー。
   - 時間切れ: `t_v` に達した。決済価格は `t_v 直前の約定価格 × (1 − s_slip)`、テイカー。
5. **手数料込みリターン**: `f_e`, `f_x` はエントリー・決済の手数料率（メイカー報酬は負の値として扱う。符号の規約は §3.5 の要検証事項に従って確定させる）。

   ```
   ret_net = (P_x × (1 − f_x) − P_e × (1 + f_e)) / (P_e × (1 + f_e))
   ```

6. **ラベル**: `ret_net > 0` なら `y = 1`、それ以外は `y = 0`。

出力（labels テーブル）: `event_id`, `filled`, `t_f`, `P_e`, `U`, `L`, `t_v`, `exit_type`（`tp` / `sl` / `time`）, `t_x`, `P_x`, `ret_net`, `y`, 使用したパラメータ一式。

前提と制約:

- 発注数量の全量が `P_e` で約定すると仮定している。この仮定は、発注量が出来高に対して十分小さい場合にしか成り立たない。
- 約定の検知から利確指値を出すまでの遅延は無視している。
- 本番の決済ロジック（Phase 7）と同じ判定関数を使えるように実装する。

テスト:

- 手作りの約定列で、利確・損切り・時間切れ・未約定の各ケースを確認する。
- `strict` と `touch` の違いを確認する。
- σ に `t0` より後のデータが使われていないことを確認する。

### Phase 4: 特徴量

すべて開始時刻が `t0` より前の足から計算する。ローリング計算は、窓が満たない区間を NaN とする（`min_periods = 窓長`）。

| 特徴量 | 定義 |
|---|---|
| `ret_k` | 直近 k 本の対数リターン（k = 1, 4, 16, 96） |
| `rv_k` | 直近 k 本の `r` の標準偏差（k = 16, 96） |
| `pk_vol_k` | Parkinson ボラティリティ `sqrt(mean(ln(high/low)²) / (4 ln 2))`（k = 16, 96） |
| `vol_z` | log(volume) の直近96本に対する z スコア |
| `imb_k` | 直近 k 本の `Σ(buy_volume − sell_volume) / Σ volume`（k = 4, 16） |
| `ntrades_z` | 約定件数の直近96本に対する z スコア |
| `large_share_k` | 直近 k 本の `Σ large_volume / Σ volume` |
| `empty_share` | 直近96本に占める約定なしの足の割合 |
| `dist_ma_n` | `(close − SMA_n) / (σ × close)`（n = 16, 96） |
| `cusum_ratio` | `|s_value| / h` |
| `sigma` | `t0` 時点の σ |
| `hour_sin`, `hour_cos`, `dow_sin`, `dow_cos` | 時刻・曜日の周期エンコード |

線形モデルで標準化が必要な場合は、学習側の fold だけで平均と分散を推定する。

### Phase 5: メタモデル

**学習データ**: Phase 3 で約定したイベントのみを使う。発注の期待値は `P(約定) × E[損益 | 約定]` であり、未約定なら損益は 0 になる。したがって発注すべきかどうかは `E[損益 | 約定]` の符号で決まり、約定したイベントだけで学習すれば足りる。未約定イベントは約定率の分析に使う。

**モデル**: 【確定】D6 に従い、`dip` と `breakout` で別々のモデルを学習して比較する。

- ベースライン: ロジスティック回帰
- 主モデル: 勾配ブースティング（LightGBM など）

**サンプル重み**: ラベル期間 `[t_f, t_x]` の重なりから平均ユニークネスを計算して重みにする（同書 4.4 節）。

**交差検証**: Purged K-fold（同書 7 章）。テスト側のラベル期間 `[t0, t_x]` と重なる学習サンプルを除外し、各テスト区間の直後にエンバーゴ期間（初期値 `N_v` 本分）を設ける。

**ホールドアウト**: 直近の一定期間はモデル選択に一切使わない。期間の長さは【未決】U5。

**評価指標**: log loss、AUC、しきい値ごとの precision / recall、確率の較正。最終判断は Phase 6 のバックテストで行う。

**成果物**: モデルファイルと、次のメタデータを一緒に保存して再現できるようにする。特徴量一覧、パラメータのハッシュ、学習期間、データのバージョン、`signal_type`。

### Phase 6: バックテスト

約定の生データ上でイベント駆動のシミュレーションを行う。約定・決済の判定には Phase 3 と同じ関数を使う。

ルール:

1. ペアごとに同時に持てるポジションは1つ。エントリー注文の待機中またはポジション保有中は、新しいイベントを無視する。
2. 発注量はメタモデルの予測確率から決める（同書 10.3 節の方式）。比較用に、`p ≥ θ` のとき固定額で発注するしきい値方式も実装する。
3. 発注量が `max(unit_amount, min_amount)` 未満なら発注しない。

レポートに含める項目:

- 手数料込みの累積リターン、取引回数、約定率、勝率、平均利益・平均損失、最大ドローダウン、シャープレシオ、保有時間の割合、手数料の内訳（メイカー報酬とテイカー手数料）
- `exit_type` ごとの件数と損益

比較対象:

- メタモデルなし（一次シグナルのみ）
- バイ・アンド・ホールド
- 同じ頻度のランダムエントリー

過学習の管理: 試行したパラメータの組み合わせ数を実験ログに記録し、多重検定を考慮した評価（例: Deflated Sharpe Ratio）を行う。ウォークフォワードでの再学習頻度は【未決】U5。

### Phase 7: 本番実行

Phase 6 の結果をオーナーが確認してから着手する。

**7.1 実行モード**

| モード | 内容 |
|---|---|
| `dry-run` | 実際の市場データを使い、約定は Phase 3 と同じ規則でシミュレーションする。既定のモード |
| `live-small` | 最小に近い数量で実際に発注する。V6 の検証もここで行う |
| `live` | 通常運用。明示的なフラグと確認がなければ起動しない |

**7.2 判断ループ（15分ごと）**

1. 足の終了時刻から数秒待ち、遅れて届く約定を取り込む。
2. Public Stream で受信した約定から、`aggregate_trades` で最新の足を作る。受信の欠落があれば REST の約定履歴で補完する。
3. CUSUM を更新する。イベントがあれば特徴量を計算し、メタモデルで確率と発注量を求める。
4. 発注前チェック:
   - `/spot/status` が `HALT` でない。数量が `min_amount` 以上
   - `circuit_break_info.mode` が `NONE`（CB 中は post_only が無効になるため新規エントリーしない）
   - `/spot/pairs` の停止フラグ（`stop_order`, `stop_buy_order` など）が立っていない
   - 円残高の `free_amount` が足りる
   - リスク制限（7.4）に抵触しない
5. `min(P_e, 最良買気配)` で post_only 買い指値を出す。
6. `T_fill` 以内に約定しなければ取り消す。一部約定していれば、約定分をポジションとして扱う。
7. 約定したら（Private Stream の通知、または注文照会で確認）、約定数量で post_only 売り指値を `U` に出す。
8. Public Stream の約定を監視し、`price ≤ L` になるか `t_v` に達したら、利確指値を取り消す → 取消完了と `free_amount` を確認する → 成行で売る。
9. 判断内容、注文、約定、エラーをすべて記録する。

**7.3 注文の状態遷移**

| 現在の状態 | 事象 | 次の状態 | 処理 |
|---|---|---|---|
| `IDLE` | エントリー判断が出た | `ENTRY_PENDING` | post_only 買い指値を出す |
| `ENTRY_PENDING` | 全量が約定した | `POSITION_OPEN` | 約定数量で post_only 利確指値を出す |
| `ENTRY_PENDING` | `T_fill` 経過、未約定 | `IDLE` | 買い指値を取り消す |
| `ENTRY_PENDING` | `T_fill` 経過、一部約定 | `POSITION_OPEN` | 残りを取り消し、約定数量で利確指値を出す |
| `POSITION_OPEN` | 利確指値が全量約定した | `IDLE` | 記録する |
| `POSITION_OPEN` | 損切り条件または時間切れ | `EXITING` | 利確指値を取り消す |
| `EXITING` | 取消の完了と `free_amount` を確認した | `EXITING` | 残数量を成行で売る |
| `EXITING` | 成行売りが約定した | `IDLE` | 記録する |

異常時の扱い:

| 事象 | 対応 |
|---|---|
| post_only 指値が即時に拒否・取消された | そのイベントは見送る（挙動は §3.6-6 で要検証） |
| 利確指値の取消に失敗し、すでに約定していた | 利確で決済済みとして扱う |
| 利確指値が一部約定した後に損切り条件に達した | 残りを取り消し、残数量だけを成行で売る |
| 成行売りが 70020（CB 中）で拒否された | 【未決】U6 |
| Public Stream の切断 | バックオフ付きで再接続する。切断中は REST で補完する。データが一定時間更新されなければ新規エントリーを止める |
| Private Stream トークンの期限切れ（12時間） | `/user/subscribe` で再取得する。通知が途絶えている間は注文照会のポーリングで補う |
| HTTP 429 | バックオフする。更新系は毎秒6回を超えないように送信を制御する |
| プロセスの再起動 | `active_orders` と `assets` から状態を復元してから再開する |

**7.4 リスク管理**

次の項目を実装する。値はすべて【未決】U2。

- キルスイッチ（手動操作と、自動発動の両方）
- ペアごとの最大ポジション金額
- 1日の損失上限
- 連続損失回数の上限
- データ更新が途絶えたときの新規エントリー停止

**7.5 秘密情報**

API キーとシークレットは環境変数またはシークレット管理サービスから読み込む。ログには出力しない。リポジトリにはコミットしない。API キーには出金権限を付けない。

**7.6 記録**

判断（特徴量、予測確率、モデルのバージョン）、注文のリクエストとレスポンス、約定、エラーを追記専用の形式で保存する。API からは3か月より前の注文を取得できないため、この記録が唯一の履歴になる。

**7.7 時刻同期**

ACCESS-REQUEST-TIME の検証があるため、実行環境を NTP で同期する。

## 6. 非機能要件

- ログは標準の `logging` モジュールで出力する。

4. 各フェーズで、テストの追加と、`README.md` および本書の更新を行う。
5. 実注文を出すコードは `dry-run` を既定にする。
6. 秘密情報をコミットしない。
7. 公開 API に大量のリクエストを送らない（レート制限の数値が不明なため）。
